# RailMate 答辩与演示导读（评委友好版）

> **一句话**：RailMate 把铁路出行从「打开 App 填表」变成「说一句人话 → AI 规划 → 结构化卡片可点 → 演示闭环可验」——**决策在对话里完成，执行在卡片里落地**。

---

## 1. 评委 60 秒：为什么不是又一个聊天机器人？

| 维度 | 常见做法 | RailMate |
|------|----------|----------|
| 查票 | 用户自己选站、选日期、筛车次 | 自然语言 + 位置补全 + Agent 自动调工具 |
| 结果 | 长文本罗列车次 | **工具 JSON → 前端卡片**（车次 / 中转），可点进详情 |
| 交互 | 只有打字 | **快捷回复按钮**（点选即发送）、语音、GUI 查票并存 |
| 闭环 | 停在「告诉你有哪趟车」 | **演示购票 → 行程 → 电子检票链接（真实 URL 触发后端状态）** |
| 工程 | Demo 感 | **SSE 规划进度、中转并行查询、hydration 与合规边界可讲** |

**金句备选（答辩收尾用）：**

1. *「我们卖的不是模型接口，是铁路场景里可编排的决策链。」*
2. *「对话负责理解意图，卡片负责承载结构化真相；二者缺一都不是 Agent 产品。」*
3. *「演示票务与真实 12306 边界划清，是为了证明：创新可以在合规沙盘里把体验跑通。」*

## 2. 三分钟演示脚本（建议顺序）

| 秒数 | 动作 | 台词要点 |
|------|------|----------|
| 0:00–0:20 | 打开首页对话 | 「用户不说站名、只说要中转——Agent 会追问还是直接查？」→ 展示**上下文与偏好**（右侧栏）。 |
| 0:20–0:55 | 输入：中转/多方案需求 | 强调**工具调用 + SSE 进度条**（不是黑盒等很久）；结果以**卡片**出现，勿只念文字。 |
| 0:55–1:25 | 点进车次详情 → 演示购票 | 「交易链路在真网是重的，我们用**本地演示订单**把产品故事讲完。」 |
| 1:25–1:55 | 打开行程 → 检票凭证 | 展示 **二维码 = 后端检票 URL**；手机或新标签打开 → **HTML 检票成功页** + 列表变「已检票」；**已检票不可退票**（规则清晰）。 |
| 1:55–2:20 | 查票页 | **车次类型仅前端筛选**、API 一次拉全量——体现工程上的「职责分离」。 |
| 2:20–2:45 | 设置页「演示模式」 | 一句话：**模拟数据、本机存储、不碰真实订单**——合规与产品诚实。 |
| 2:45–3:00 | 收尾 | 点题：**决策 AI + 铁路工具中台 + 可演进交易路径**。 |

## 3. 近期可讲的「硬」迭代（区别于初版原型）

- **体验**：对话 **快捷回复** `::actions::`（文中任意位置解析，避免模型插错行就整段露馅）；卡片列表**头图路线**按真实结果聚合站名。
- **可信**：**电子检票**走真实 GET 链接改订单状态，成功页展示订单号、**乘车人**、车次、时间——Demo 也要「像真的」。
- **性能**：中转查询 **hub 并行**、线程池收紧；LLM **超时重试 / max_tokens**；SSE **短轮询队列**避免 Ctrl+C 卡死。
- **前端工程**：**挂载门控 + 延后 CssBaseline** 治理 hydration；查票日期 **useSyncExternalStore** 避免 SSR/客户端日期差；**双清除钮**与 MUI Autocomplete **disableClearable** 去重。

## 4. 评委常问 → 预备答法（简版）

**Q：和直接接 ChatGPT 有啥区别？**  
A：我们有**铁路专属工具链**（直达/中转/停留/时刻/定位）和**结构化卡片渲染**，模型不能编造余票票价；边界在工具返回值上。

**Q：演示购票是不是假的？**  
A：是**与生产隔离的本地演示**，但交互与状态机（购退检）完整，用于验证产品与联调；真交易需接官方支付与签约。

**Q：数据从哪来？**  
A：官方查询能力与本地缓存结合；不鼓励违规抓取，**频率与鉴权可控**（详见技术架构「合规」章节）。
