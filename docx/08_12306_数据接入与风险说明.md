# RailMate 与 12306 数据接入说明（接口、实现、差异与风险）

## 1. 文档目的

说明：本项目**从中国铁路客户服务中心网站 `kyfw.12306.cn` 上，与官方 Web 页面相同源的 HTTP 接口**拉取哪些数据、如何接入、为何常见「简单脚本」容易失败，以及团队需要意识到的**合规与工程风险**。  

**重要说明**：12306 **未对外提供面向第三方的公开 API 文档**；本项目代码中的封装是**基于网页行为的非官方实现**，可能随官方改版而失效，需持续维护。

---

## 2. 我们实际用到的接口（按数据类型）

以下 URL 均来自 `app/services/railway_api.py` 等模块，与官网 PC 端余票查询、公布票价、经停站等页面同源。

| 用途 | 典型路径 | 说明 |
|------|----------|------|
| **站点列表** | `/otn/resources/js/framework/station_name.js` | 返回一段 JavaScript，内含全国车站名、电报码、拼音等；解析后用于站名与电报码互转。 |
| **余票 / 车次列表** | `/otn/leftTicket/queryZ`、`queryA`、`query`、`queryT` | 按日期、出发/到达电报码查询当日车次；返回 JSON，其中 `data.result` 为字符串数组，每条为**管道符 `|` 分隔**的字段，需自行解析（车次号、时刻、余票等）。代码会**依次尝试**多个 query 变体，并记住「最近成功」的 URL，减轻 12306 侧路由变化带来的影响。 |
| **余票查询（同能力）** | `leftTicket/query`（历史路径） | 与上列同类能力，保留在常量中便于对照。 |
| **实时票价（更细）** | `/otn/leftTicket/queryTicketPrice` | 需车次内部编码、站序等参数；服务端对** Cookie / 会话**要求较严，返回 HTML 或空时通常表示鉴权不足。 |
| **公布票价（公开）** | `/otn/leftTicketPrice/queryAllPublicPrice` | 与官网「公布票价」查询页同源，**不依赖登录**即可作为票价回退；Referer 需指向 `queryPublicIndex` 等页面。 |
| **经停站 / 时刻** | `/otn/czxx/queryByTrainNo` | 根据车次内部编码、起止电报码、日期查询停靠站列表。 |
| **会话初始化** | `GET /otn/leftTicket/init` | 先建立 HTTP 会话，获取 `JSESSIONID` 等基础 Cookie，便于后续请求不被直接返回整页 HTML。 |

**认证相关（扫码登录，非「爬虫」数据接口，而是走官方登录流程）**（`app/services/railway_auth.py`）：

| 步骤 | 路径 | 作用 |
|------|------|------|
| 申请二维码 | `GET /passport/web/create-qr64` | 获取二维码 UUID 与图片。 |
| 轮询扫码 | `POST /passport/web/checkqr` | 判断用户是否已扫描、确认。 |
| 登录令牌 | `POST /passport/web/auth/uamtk` 等 | 扫码成功后换取 `uamtk`，再在 `/otn/uamauthclient` 完成 OTN 侧登录，**收集完整 Cookie**。 |

## 3. 项目里「怎么搞的」（实现要点）

### 3.1 模拟浏览器 XHR

对 `kyfw.12306.cn` 的请求使用与常见浏览器一致的 `User-Agent`、`Accept`、`Referer`、`X-Requested-With: XMLHttpRequest` 等，减少被直接返回 **HTML 整页**而非 JSON 的概率（代码注释中明确提到这一点）。

### 3.2 会话与 Cookie 分层

- **基础会话**：单例 `httpx.Client` 先访问 `leftTicket/init`，在客户端 Cookie Jar 中保留 `JSESSIONID` 等，供余票、公布票价等接口共用。  
- **票价接口 `queryTicketPrice`**：在「已有会话 Cookie」基础上，再按请求合并额外 Cookie，**避免**用手写 Cookie 字符串覆盖掉整个 Jar（否则会把会话初始化得到的 Cookie 弄丢）。  
- **Cookie 优先级**（用于 `queryTicketPrice` 等）：  
  1. 环境变量 `railway_12306_cookie`（若配置）  
  2. 用户 **12306 扫码登录** 后的账户 Cookie（`12306_session.json` 持久化，约 30 天）  
  3. **设备类 Cookie**（见下节）

### 3.3 设备 Cookie：Playwright 子进程

`app/services/railway_device.py` 使用 **Playwright** 在无头 Chromium 中打开 `leftTicket/init`，读取 `RAIL_DEVICEID`、`RAIL_EXPIRATION` 等 Cookie。  

- 在**独立子进程**中执行，避免与主进程 asyncio 冲突。  
- **后台守护线程**约每 6 小时刷新一次；`get_12306_device_cookies()` 非阻塞，缓存未就绪时可能返回空字典。  
- 这是许多「只写 requests」的项目**没有**做的一步，也是部分票价/风控接口**更容易失败**的原因之一。

### 3.4 业务层行为

- **余票**：`query_tickets` 解析管道分隔字符串，映射商务/一等/二等/卧铺/硬座/无座等字段（索引可能随官方变化，需维护）。  
- **票价**：优先精确票价；失败或为空时，用 **公布票价接口** 按车次号匹配（`source` 在 API 中为 `12306_live_precise` / `12306_public` / `unavailable` 等）。  
- **失败回退**：`TrainService` 在 Live 模式异常时可回退本地 Mock 数据（见 `train_service.py`）。  

### 3.5 产品边界（与真实下单无关）

演示购票、订单等仍写入**本地数据库**；**不会**通过本项目的 HTTP 封装去代替用户在 12306 官方渠道完成真实支付、占座、改签（见 `app/models/ticketing.py` 等注释及架构文档）。

## 4. 为什么「别人都不行」或容易踩坑（工程视角）

此处「不行」指：**不稳定、全站返回 HTML、票价为空、频繁被限流或封禁**，并非说别人绝对无法访问。

1. **没有公开 API 与契约**  
   字段顺序、query 路径（`queryZ`/`queryA` 等）、返回 JSON 结构都可能变化；必须**读页面或抓包**维护，成本高。

2. **反自动化与风控**  
   12306 会按 IP、频率、Cookie、设备指纹、TLS/行为特征等做限制；裸 `curl` 或简单脚本容易被挡或返回非 JSON。

3. **Cookie 与登录态差异**  
   - 余票查询在**仅会话**下往往可用；  
   - **精确票价**等接口更依赖 **设备 Cookie 或登录 Cookie**；  
   未做「init 会话 + 设备/登录 Cookie」时，**票价经常为空**，看起来像「接口坏了」。

4. **Referer 与入口差异**  
   公布票价等接口要求 Referer 指向对应官方页面，否则可能被拒绝或返回异常。

5. **解析复杂度**  
   余票结果是**长字符串管道格式**，不是稳定 schema；不同车型、临客、字段缺失都要做防御性解析。

## 5. 风险清单（团队必须知情）

### 5.1 合规与条款风险

- 使用非官方接口、自动化访问可能违反 **12306 用户协议或网站条款**；若用于商业产品，需**法务评估**是否需官方合作或授权渠道。  
- 本文档仅作**技术说明**，不构成法律意见。

### 5.2 稳定性与维护风险

- 接口 **随时变更**；需专人跟进、监控报警、快速降级（Mock / 缓存 / 提示用户前往官方 App）。  
- 春运等高峰期的限流、风控加强可能导致 **可用性骤降**。

### 5.3 安全与隐私风险

- **扫码登录 Cookie** 与 **设备 Cookie** 具有较高权限，**必须**限制文件访问权限（`12306_session.json` 已在 `.gitignore`）、服务器安全加固；泄露即可能导致账号被他人滥用。  
- 若将 Cookie 写入环境变量，注意**不要在日志、CI 日志、前端暴露**。

### 5.4 依赖与运维风险

- Playwright + Chromium 增加**部署体积**与**资源占用**（内存、无头浏览器）；容器/服务器需安装浏览器依赖或采用官方镜像策略。  
- 子进程超时（如 60s）未拿到设备 Cookie 时，部分功能降级。

### 5.5 数据准确性风险

- 余票「有/数字」与票价、公布票价与执行票价可能**存在业务差异**；应以用户**最终下单前**在官方渠道为准。  
- 解析错误字段时可能展示**错误余票或票价**，需产品侧提示「仅供参考」。

### 5.6 声誉与商业风险

- 若对外宣称「官方 API」而实际为网页封装，可能引发**误导**与投诉；对外话术建议明确为「**查询能力对接官网公开页面同源接口，以官方为准**」。
